## What's next
- **✅ S3 desktop↔desktop gate PASSES 2026-08-08 against the DEPLOYED production relay — two real defects found and fixed.** Re-verified live after the fix: restore held for 4 min with no resurrection (was: reverted at +50 s), reorder propagates in 3 s (was: 63 s), text still <5 s, and the losing device keeps the discarded content as a recoverable safety snapshot. Gates: eslint 0, tsc 0, vitest 1950 pass / 6 known eval-rig failures. Fixes in `src/sync/engine.ts` + new `src/sync/answerFrame.ts`, covered by 3 regression tests in `engineMetaEpoch.test.ts` (all three verified to FAIL without the fix):
  1. **Resurrection (data-loss-shaped).** A device that is *behind* — knows a restore bumped the epoch but has not applied the replacement — still published its own copy stamped at the NEW epoch, and `EpochManager.accepts()` cannot tell that copy from the restored one, so the restoring device merged the discarded text back in and undid its own restore. `makeHelloDoc` already guarded the advertise side (empty state vector when behind); the send side had no such guard. Now `answerFrame()` withholds a scene we owe a replacement for, and the live-doc listener stays quiet while behind.
  2. **Structure changes waited for the peer's 60 s sweep.** `sendTargetedHello` only ADVERTISES a state vector, and `answerHello` replies with what the PEER lacks — so a local reorder was never actually pushed by that exchange; it sat until the peer's own sweep came asking. Scenes are covered by the live-doc channel, meta docs had nothing, so a local meta save now pushes its content directly (echo-safe: remote applies write via `metaStore.save()`, which does not notify `saveListeners`).
  3. **Restore delivery waited for the peer's sweep (20–50 s), then didn't apply when it did arrive.** Two more causes, both closed 2026-08-08. (a) Restores run inside `syncEngine.pause()` (`App.snapshots.ts`) and `sendMessage` drops everything while paused, so nothing was pushed at all — replacements are now held in `ReplacementQueue` and flushed on resume/reconnect, meta frame FIRST then the scene as a full state. (b) `provider.subscribeFrames` was fire-and-forget (`void this.onBlob(...)`), so the meta+scene pair raced on the receiving device: the short scene path finished first, `accepts()` rejected it against the still-stale epoch, and the device then waited a full sweep for a replacement it had already thrown away. Inbound frames are now applied in arrival order through a promise chain. Found by instrumenting the live pair — the sender's console proved it pushed both frames 104 ms after the restore, which moved the search to the receiver.
  4. **A remote epoch bump could be misread as a LOCAL restore** (found by the codex adversarial review, confirmed in code). `mergeMeta` persisted the incoming meta at `engine.ts:304`, then awaited the SQL projection, and only called `readMetaUpdate` afterwards. A local structure edit landing in that window read the already-persisted remote bump, so `recordLocal()` saw `epoch > known`, marked it applied, and pushed our STALE scene at the new epoch — resurrection again, through the new replacement queue. `readMetaUpdate` now runs in the same continuation as the save, before any further await.
  - **Measured live, both peers on the deployed relay: restore 1 s (was 20–50 s), reorder 3 s (was 63 s), scene text ~1 s.** No resurrection across 2-minute watches, before and after the review fixes. Gates: eslint 0, tsc 0, vitest 1954 pass.
  - **Accepted limitations (documented, not fixed):**
    - **Concurrent restores on two devices are not safe.** `docEpochs` is a plain `Y.Map` number register (`metaDoc.ts` `bumpEpoch`), so two simultaneous bumps can merge to the LOWER value, leaving devices with different `known` epochs that reject each other's frames; and two restores that both land on the same epoch each consider themselves applied and merge rather than picking a winner. Needs a monotonic representation (per-device counters, take the max) before restore-wins can be called correct under concurrency. Pre-existing, not introduced here.
    - **If the restoring device vanishes mid-handoff, peers stay behind on that scene indefinitely.** They withhold their stale copies (correct — publishing is the resurrection bug) but nobody can supply the replacement, and the relay stores no history. Non-destructive: each device keeps its own content locally; the scene simply stops converging until the restoring device returns.
    - **A meta-only targeted hello can provoke the peer to answer with full state for every doc it holds** (`answerHello` iterates all docs; missing vectors force full sends). Bandwidth amplification, pre-existing, worth revisiting if sync ever feels heavy on large libraries.
- **Full-suite flakiness is RESOURCE EXHAUSTION, not test isolation — use `npm run test -- --maxWorkers=4` on a loaded machine.** `goalsP6.acceptance.test.ts` ("GoalRing is exported…") and friends fail intermittently in full runs and always pass alone. My first read (files sharing a vitest worker) was WRONG: vitest 4 already runs `isolate: true` on the `forks` pool, so per-file module registries are not shared. The real mechanism, diagnosed by a codex dispatch and then confirmed here: vitest defaults to ~15 forked workers on this 16-CPU box, and the machine accumulates long-lived node processes across sessions (measured 192 node processes — ~128 orphaned MCP servers dating back days, 44 tsservers — with only 4.5 GB of 32 GB free). Workers then fail to start ("Failed to start forks worker" / "Timeout waiting for worker to respond") and their files report as failures. Evidence: unbounded runs gave 7 failures including GoalRing; `--maxWorkers=4` gave exactly the 6 known eval-rig failures across all 201 files. Adding any test file can shift which heavy files overlap, which is why an unrelated sync test appeared to cause it. If a full run shows unfamiliar failures, re-run bounded before believing them — and consider killing stale MCP/tsserver node processes.
